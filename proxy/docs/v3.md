# Geocoder v3 API

Geocoding and reverse geocoding for Norwegian addresses, stop places, and points of interest.

## API Spec

- OpenAPI spec: `GET https://api.dev.entur.io/geocoder/v3/openapi.yaml`
- Swagger UI: https://petstore.swagger.io/?url=https://api.dev.entur.io/geocoder/v3/openapi.yaml

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v3/autocomplete` | Search for places by text query |
| GET | `/v3/reverse` | Convert coordinates to nearby places |
| GET | `/v3/place` | Look up one or more places by ID |

## Quick start

```bash
# Autocomplete
curl "https://api.entur.io/geocoder/v3/autocomplete?q=Oslo+S"

# Autocomplete with focus point (boost results near a location)
curl "https://api.entur.io/geocoder/v3/autocomplete?q=haugen&lat=59.9&lon=10.7"

# Reverse geocode (radius in km, decimals accepted)
curl "https://api.entur.io/geocoder/v3/reverse?lat=59.9110&lon=10.7522&radius=0.5"

# Place lookup
curl "https://api.entur.io/geocoder/v3/place?ids=NSR:StopPlace:337"
```

## Defaults

| Parameter | Default |
|-----------|---------|
| `limit` | `10` |
| `lang` | `"no"` |
| `radius` (autocomplete focus) | `50` km |
| `weight` (autocomplete focus) | `0.5` |
| `multimodal` | `"parent"` |

|----|----|-------|

#### Place (`/v3/place`)

| v2 | v3 | Notes |
|----|----|-------|

#### Removed across the board

- `categories` is not currently exposed in v3. Stop place categorisation is returned in the response (`stopPlaceTypes`, `categories`) but not accepted as a filter.

#### `layers`

| v2 `layers` | v3 `layers` |
|-------------|------------|
| `address` | `address` |
| _(no equivalent)_ | `street` |
| `venue` | `stopPlace` |
| _(no equivalent)_ | `groupOfStopPlaces` |
| _(no equivalent)_ | `poi` |
| _(no equivalent)_ | `place` |

The "no equivalent" entries are (mostly) not new data - they were always indexed, just lumped under v2's two coarse layers. In v2 `venue` held NSR stop places only; everything else fell under `address`. v3 splits them out so each result carries a meaningful `layer`:

| v3 `layer` | data origin | v2 layer it lived under |
|------------|-------------|-------------------------|
| `address` | matrikkel | `address` |
| `street` | matrikkel | `address` |
| `stopPlace` | NSR stop places | `venue` |
| `groupOfStopPlaces` | NSR group of stop places | `address` |
| `poi` | OSM POIs, `custom-poi` (new in v3) | `address` / new |
| `place` | kartverket-stedsnavn (cities, districts) | `address` |

The `custom-poi` source is the one genuine new entry; everything else is the same indexed data with a more specific label.

**Default behaviour (no `layers` filter):** the result *set* is the same as v2 - only the `layer` value attached to each result changed. All layers are eligible, with one server-side exclusion: addresses are hidden from autocomplete unless the query text contains a digit, or `sources` explicitly includes `kartverket-matrikkelenadresse`. Reverse hides addresses unless the caller opts in via `sources=kartverket-matrikkelenadresse` or `layers=address`. The OpenAPI schema cannot express these conditional exclusions; they are server-side behaviour.

#### `sources`

| v2 | v3 |
|----|----|
| `openstreetmap` | `openstreetmap` |
| `openaddresses` | `kartverket-matrikkelenadresse` |
| _(no equivalent)_ | `kartverket-stedsnavn` |
| _(no equivalent)_ | `nsr` |
| _(no equivalent)_ | `custom-poi` |

#### Weight semantics (changed)

`weight` is renamed straight across from `focus.weight`, but the math is different. In v2 it was an open-ended scalar fed through a curve (default ~15). In v3 it is a linear bias on a 0-1 scale:

- `weight=0` - no focus bias, results ranked purely on text/importance.
- `weight=1` - maximum focus bias, results near the focus point dominate.
- `weight=0.5` (default) - balanced bias: importance and proximity contribute roughly equally to ranking.

The v3 default tilts toward importance more than v2 does, so far-away major cities can still win against near-focus same-prefix streets (e.g. "Bergen" from Oslo still returns Bergen, not Bergensgata). If you tuned `focus.weight` in v2 do not just copy the number across.

#### Default radius differs from v2

v2's nominal default for `focus.scale` is 2500 km, v3's default for `radius` is 50 km. They are not equivalent values - they produce similar effective focus behaviour.

v2 runs `focus.scale` through a tanh saturation curve before mapping to a Photon zoom: any value past ~300 km saturates, so `focus.scale=2500` collapses to roughly the same Photon zoom as `focus.scale=300` (biasRadius ~120 km). The 2500 number is a Norway-coverage placeholder, not a literal radius.

v3's `radius` is the inverse of Photon's biasRadius formula with no saturation, so the number you pass *is* the effective focus radius: `radius=50` means biasRadius ~21 km, `radius=100` means ~46 km. Set `radius=2500` in v3 and you get essentially no focus bias (biasRadius ~1700 km swallows the country).

If you previously sent `focus.scale=2500` in v2 and want comparable behaviour in v3, use `radius` somewhere in the 50-150 km range, not 2500.

#### Focus parameters only take effect together

`lat`, `lon`, `radius`, and `weight` on `/v3/autocomplete` are a bundle. Sending any of them without both `lat` and `lon` is a 400 error - the proxy refuses to silently drop bias parameters. The OpenAPI schema cannot express this co-dependency.

#### `multimodal`

Applies to `/v3/autocomplete` and `/v3/reverse`.

An NSR multimodal stop groups several stop places (e.g. a bus terminal + train station hub) under a parent. Most NSR stop places are *monomodal* - standalone, not part of any such group - and those always appear in results regardless of this parameter. `multimodal` only decides whether multimodal parents, children, or both come through alongside them.

- `parent` (default) - monomodal stops + multimodal parents; multimodal children hidden.
- `child` - monomodal stops + multimodal children; multimodal parents hidden.
- `all` - monomodal stops + multimodal parents + multimodal children.

### ID format

v3 uses canonical, fully-qualified IDs. v2 uses legacy/abbreviated forms for backwards compatibility.

| Entity | v2 ID | v3 ID |
|---|---|---|
| Stop place | `NSR:StopPlace:N` | `NSR:StopPlace:N` |
| Group of stop places | `NSR:GroupOfStopPlaces:N` | `NSR:GroupOfStopPlaces:N` |
| OSM POI | `OSM:TopographicPlace:N` | `OSM:TopographicPlace:N` |
| Matrikkel address | bare numeric (e.g. `225678815`) | `KVE:PostalAddress:N` |
| Matrikkel street | `KVE:TopographicPlace:KOMNR-NAME` | `KVE:TopographicPlace:KOMNR-NAME` (unchanged) |
| Stedsnavn place | bare numeric (e.g. `434810`) | `KVE:PlaceName:N` |
| Boundary filter (kommune/fylke code) | bare numeric (e.g. `0301`, `03`) | `KVE:TopographicPlace:N` |
| Grunnkrets (in `address.boroughId`) | `whosonfirst:borough:N` | `KVE:Borough:N` (N = 8-digit grunnkretsnummer: KOMNR + 4-digit sequence, e.g. `34200205`) |

In v2 **bare numerics on the wire are ambiguous**: they can be stedsnavn places (stripped from `KVE:PlaceName:`) or postal addresses (stripped from `KVE:PostalAddress:`). v3 removes this ambiguity by giving each entity a fully-qualified namespace.

**Namespaces carry the type.** Stedsnavn (`KVE:PlaceName:`) and grunnkrets (`KVE:Borough:`) live in dedicated namespaces and are unambiguous on the namespace alone. Within `KVE:TopographicPlace:` the remaining three uses are distinguished by suffix format and context:

| Entity | Suffix shape | Context |
|---|---|---|
| Fylke | 2-digit code, no hyphen (`03`) | `address.countyId` only |
| Kommune | 4-digit code, no hyphen (`0301`) | `address.localityId` only |
| Street | `KOMNR-<name>` (`0301-Storgata`) | top-level `id` |

SSR subtype (`by`/`bydel`/`tettsted`/`tettsteddel`/`tettbebyggelse`) is not surfaced in the response - all five collapse to `layer=place`.

**Photon-safe ID lookups.** Photon's category filter only accepts `[a-zA-Z0-9_.-]`. Street IDs carry names with spaces and Norwegian characters, so both the converter (index side) and the proxy (query side) apply an identical transliteration when turning IDs into category terms: å -> aa, ø -> oe, æ -> ae, space and other characters -> `_` (e.g. `KVE:TopographicPlace:3407-Fahlstrøms plass` -> `KVE.TopographicPlace.3407-Fahlstroems_plass`). The JSON `id` field keeps the original characters; the transliteration is internal to index/lookup.

### Response format

Both v2 and v3 return a GeoJSON `FeatureCollection`. High-level shape changes:

- Feature `properties` use structured objects (`name`, `address`, `transportModes`) instead of v2's flat fields.
- A `metadata` object at the top level replaces v2's `geocoding` block. It carries the echoed query, `resultCount`, and an ISO 8601 `timestamp`. Errors come back as HTTP 4xx with a JSON body rather than under `geocoding.errors`.
- `/v3/reverse` responses include `distance` on each feature, in kilometres with 3-decimal precision (same units as v2).

The per-property table below is authoritative; see [layers](#layers) and [sources](#sources) for value-set changes on `layer` and `source`.

#### Property mapping (`properties.*`)

Field-by-field migration. Anything not listed is unchanged; anything marked `_(removed)_` has no v3 equivalent.

| v2 | v3 | notes                                                                                                                                                            |
|---|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `id` | `id` | ID shape differs - see [ID format](#id-format)                                                                                                                   |
| `name` | `name.default` |                                                                                                                                                                  |
| `label` | `name.display` | formatted display name with locality context                                                                                                                     |
| `popular_name` | `name.label` | colloquial name; rarely populated today                                                                                                                          |
| `housenumber` | `address.houseNumber` |                                                                                                                                                                  |
| `street` | `address.streetName` |                                                                                                                                                                  |
| `postalcode` | `address.postalCode` |                                                                                                                                                                  |
| `country_a` / `countrycode` | `address.countryCode` | v2 was ISO 3166-1 alpha-3 (`"NOR"`) on `country_a`; `countrycode` was declared but never populated. v3 collapses both into `countryCode` as alpha-2 lowercase (`"no"`). Case-sensitive client comparisons will break silently. |
| `county` | `address.county` |                                                                                                                                                                  |
| `county_gid` | `address.countyId` | v2 prefixed `whosonfirst:county:`; v3 returns the raw indexed ID (e.g. `KVE:TopographicPlace:03`)                                                                |
| `locality` | `address.locality` |                                                                                                                                                                  |
| `locality_gid` | `address.localityId` | v2 prefixed `whosonfirst:locality:`; v3 returns the raw indexed ID                                                                                               |
| `borough` | `address.borough` |                                                                                                                                                                  |
| `borough_gid` | `address.boroughId` | v2 returns `whosonfirst:borough:N`; v3 returns `KVE:Borough:N` where N is the grunnkretsnummer (Norwegian sub-municipal statistical unit) |
| `city` | `address.locality` | v2 carried both `city` and `locality` for the same value; v3 keeps only `locality`                                                                               |
| `layer` | `layer` | new enum values; see [layers](#layers)                                                                                                                           |
| `source` | `source` | NSR stops normalised: v2 returned `"openstreetmap"` (multimodal parent), `"geonames"` (child), or `"whosonfirst"` (standalone); v3 always returns `"nsr"`. `openaddresses` -> `kartverket-matrikkelenadresse`. See [sources](#sources). |
| `category` | `stopPlaceTypes` + `categories` | NeTEx stop place types (e.g. `railStation`) split out from OSM tags (e.g. `restaurant`)                                                                          |
| `mode` | `transportModes` | array of `{ mode, subMode }` objects instead of pair-encoded JSON                                                                                                |
| `tariff_zones` | `fareZones` | **not a straight rename**. v3 `fareZones` carries only `AUTH:FareZone:ID`-shaped refs. v2's `tariff_zones` merged both `TariffZone` and `FareZone` refs for backwards compat; `TariffZone` refs are no longer surfaced in v3 responses, and `TariffZone`-shaped values sent as filter input do not match anything. |
| `distance` | `distance` | reverse only; kilometres with 3-decimal precision in both v2 and v3                                                                                              |
| `description` | `description` | per-language description. v2 shape: `[{lang: text}, ...]` (array of singleton maps). v3 shape: `{lang: text, ...}` (flat object keyed by ISO 639-2 alpha-3 code) |
| `accuracy` | _(removed)_ | Pelias-ism (`point`/`centroid`); not meaningful here                                                                                                             |
| `gid` | _(removed)_ | the Pelias `source:layer:id` triple; use `id`                                                                                                                    |
| `source_id` | _(removed)_ | duplicate of `id`                                                                                                                                                |
| `type` (in properties) | _(removed)_ | always `"Feature"` on the feature itself; the duplicate inside `properties` is gone                                                                              |

#### Autocomplete example

**v2 request:**
```
GET /v2/autocomplete?text=Nationaltheatret&lang=no&size=1&layers=venue
```

**v2 response:**
```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [10.7335, 59.9144] },
    "properties": {
      "id": "NSR:StopPlace:337",
      "layer": "venue",
      "source": "openstreetmap",
      "name": "Nationaltheatret",
      "label": "Nationaltheatret, Oslo",
      "category": ["railStation", "metroStation"]
    }
  }]
}
```

**v3 request:**
```
GET /v3/autocomplete?q=Nationaltheatret&lang=no&limit=1&layers=stopPlace
```

**v3 response:**
```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [10.73350, 59.91440] },
    "properties": {
      "id": "NSR:StopPlace:337",
      "name": { "default": "Nationaltheatret", "display": "Nationaltheatret, Oslo" },
      "layer": "stopPlace",
      "address": { "locality": "Oslo", "county": "Oslo", "countryCode": "no" },
      "transportModes": [{ "mode": "rail" }, { "mode": "metro", "subMode": "metro" }],
      "stopPlaceTypes": ["railStation", "metroStation"],
      "source": "nsr"
    }
  }],
  "bbox": [10.73350, 59.91440, 10.73350, 59.91440],
  "metadata": {
    "query": { "text": "Nationaltheatret", "limit": 1, "language": "no", "filters": { "layers": ["stopPlace"] } },
    "resultCount": 1,
    "timestamp": "2025-03-04T11:00:00Z"
  }
}
```

#### Reverse geocode example

**v2 request:**
```
GET /v2/reverse?point.lat=59.9110&point.lon=10.7522&boundary.circle.radius=0.5&size=1
```

**v3 request:**
```
GET /v3/reverse?lat=59.9110&lon=10.7522&radius=0.5&limit=1
```

**v3 response (abbreviated):**
```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [10.75220, 59.91100] },
    "properties": {
      "id": "NSR:StopPlace:337",
      "name": { "default": "Nationaltheatret", "display": "Nationaltheatret, Oslo" },
      "layer": "stopPlace",
      "source": "nsr",
      "distance": 0.012
    }
  }],
  "metadata": {
    "query": { "latitude": 59.9110, "longitude": 10.7522, "limit": 1, "language": "no" },
    "resultCount": 1,
    "timestamp": "2025-03-04T11:00:00Z"
  }
}
```

Note: `radius` is in **kilometres** in both v2 and v3, on both autocomplete focus and reverse. Decimals are accepted (e.g. `radius=0.5` for 500 metres). The per-feature `distance` on `/v3/reverse` is in the same units (km, 3-decimal precision).
