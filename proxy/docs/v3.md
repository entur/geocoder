# Geocoder v3 API

Geocoding and reverse geocoding for Norwegian addresses, stop places, and points of interest.

## API Spec

- OpenAPI spec: `GET https://api.dev.entur.io/geocoder/v3/openapi.yaml`
- Swagger UI: https://petstore.swagger.io/?url=https://api.dev.entur.io/geocoder/v3/openapi.yaml

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v3/autocomplete` | Search for places by text query |
| GET | `/v3/reverse` | Convert coordinates to nearby places |
| GET | `/v3/place` | Look up one or more places by ID |

## Quick start

```bash
# Autocomplete
curl "https://api.entur.io/geocoder/v3/autocomplete?q=Oslo+S"

# Autocomplete with focus point (boost results near a location)
curl "https://api.entur.io/geocoder/v3/autocomplete?q=haugen&lat=59.9&lon=10.7"

# Reverse geocode (radius in km, decimals accepted)
curl "https://api.entur.io/geocoder/v3/reverse?lat=59.9110&lon=10.7522&radius=0.5"

# Place lookup
curl "https://api.entur.io/geocoder/v3/place?ids=NSR:StopPlace:337"
```

## Defaults

| Parameter | Default |
|-----------|---------|
| `limit` | `10` |
| `lang` | `"no"` |
| `radius` (autocomplete focus) | `50` km |
| `weight` (autocomplete focus) | `0.5` |
| `multimodal` | `"parent"` |

#### Weight semantics (changed)

`weight` is renamed straight across from `focus.weight`, but the math is different. In v2 it was an open-ended scalar fed through a curve (default ~15). In v3 it is a linear bias on a 0-1 scale:

- `weight=0` - no focus bias, results ranked purely on text/importance.
- `weight=1` - maximum focus bias, results near the focus point dominate.
- `weight=0.5` (default) - balanced bias: importance and proximity contribute roughly equally to ranking.

The v3 default tilts toward importance more than v2 does, so far-away major cities can still win against near-focus same-prefix streets (e.g. "Bergen" from Oslo still returns Bergen, not Bergensgata). If you tuned `focus.weight` in v2 do not just copy the number across.

#### Default radius differs from v2

v2's nominal default for `focus.scale` is 2500 km, v3's default for `radius` is 50 km. They are not equivalent values - they produce similar effective focus behaviour.

v2 runs `focus.scale` through a tanh saturation curve before mapping to a Photon zoom: any value past ~300 km saturates, so `focus.scale=2500` collapses to roughly the same Photon zoom as `focus.scale=300` (biasRadius ~120 km). The 2500 number is a Norway-coverage placeholder, not a literal radius.

v3's `radius` is the inverse of Photon's biasRadius formula with no saturation, so the number you pass *is* the effective focus radius: `radius=50` means biasRadius ~21 km, `radius=100` means ~46 km. Set `radius=2500` in v3 and you get essentially no focus bias (biasRadius ~1700 km swallows the country).

If you previously sent `focus.scale=2500` in v2 and want comparable behaviour in v3, use `radius` somewhere in the 50-150 km range, not 2500.

#### Focus parameters only take effect together

`lat`, `lon`, `radius`, and `weight` on `/v3/autocomplete` are a bundle. The focus boost only activates when both `lat` and `lon` are set; `radius` and `weight` alone do nothing.

#### `multimodal`

Stop place hierarchy filter. NSR stop places are hierarchical: a parent stop place groups child stop places (quays, platforms).

- `parent` (default) - return only top-level stop places.
- `child` - return only child stop places.
- `all` - return both.

### ID format

v3 uses canonical, fully-qualified IDs. v2 uses legacy/abbreviated forms for backwards compatibility. The proxy translates between them at the boundary, so v2 clients keep seeing the legacy shapes; the underlying Photon index always stores the v3 form.

| Entity | v2 ID | v3 ID |
|---|---|---|
| Stop place | `NSR:StopPlace:N` | `NSR:StopPlace:N` |
| Group of stop places | `NSR:GroupOfStopPlaces:N` | `NSR:GroupOfStopPlaces:N` |
| OSM POI | `OSM:TopographicPlace:N` | `OSM:PointOfInterest:N` |
| Matrikkel address | bare numeric (e.g. `225678815`) | `KVE:PostalAddress:N` |
| Matrikkel street | `KVE:TopographicPlace:KOMNR-NAME` | `KVE:TopographicPlace:KOMNR-NAME` |
| Stedsnavn place | bare numeric (e.g. `434810`) | `KVE:PlaceName:N` |
| Boundary filter (kommune/fylke code) | bare numeric (e.g. `0301`, `03`) | `KVE:TopographicPlace:N` |

Why two views: the Photon index uses canonical IDs because they round-trip without loss and disambiguate entities by type. v2 keeps the legacy shapes because shipped clients (journey-planner, third-party apps) have parsed those response shapes for years; rewriting them would break consumers. v3 ends the ambiguity for new clients.

Translation lives in two places in the proxy:

- `PeliasResultTransformer.normalizeV2Id` - outbound: strips `KVE:PostalAddress:` and `KVE:PlaceName:`, and rewrites `OSM:PointOfInterest:` -> `OSM:TopographicPlace:` before returning to v2 clients.
- `PhotonFilterBuilder.normalizeTopographicPlaceId` - inbound: prefixes bare-numeric boundary filter IDs with `KVE:TopographicPlace:` before querying Photon.

In v2 **bare numerics on the wire are ambiguous**: they can be stedsnavn places (stripped from `KVE:PlaceName:`) or postal addresses (stripped from `KVE:PostalAddress:`). v3 removes this ambiguity entirely: addresses are `KVE:PostalAddress:N`, stedsnavn places are `KVE:PlaceName:N`, and the two shapes never collide. In practice the v2 autocomplete data overwhelmingly carries stedsnavn IDs (place/city names get clicked far more than individual addresses), so consumers using v2 autocomplete events as a popularity signal can treat v2 bare numerics as stedsnavn without significant data loss.

### Response format

Both v2 and v3 return a GeoJSON `FeatureCollection`. The key differences in v3 are:

- Feature `properties` use structured objects (`address`, `source`, `transportModes`) instead of flat fields
- A `metadata` object is added at the top level with query info and result count
- `label` -> `displayName`, `category` -> `stopPlaceTypes` (stop place type) and `categories` (OSM tags)
- `layer`/`source` string fields are replaced by `layer` (new values) and a structured `source` object

#### Autocomplete example

**v2 request:**
```
GET /v2/autocomplete?text=Nationaltheatret&lang=no&size=1&layers=venue
```

**v2 response:**
```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [10.7335, 59.9144] },
    "properties": {
      "id": "NSR:StopPlace:337",
      "layer": "venue",
      "source": "openstreetmap",
      "name": "Nationaltheatret",
      "label": "Nationaltheatret, Oslo",
      "category": ["railStation", "metroStation"]
    }
  }]
}
```

**v3 request:**
```
GET /v3/autocomplete?q=Nationaltheatret&lang=no&limit=1&layers=stopPlace
```

**v3 response:**
```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": { "type": "Point", "coordinates": [10.73350, 59.91440] },
    "properties": {
      "id": "NSR:StopPlace:337",
      "name": { "default": "Nationaltheatret", "display": "Nationaltheatret, Oslo" },
      "layer": "stopPlace",
      "address": { "locality": "Oslo", "county": "Oslo", "countryCode": "no" },
      "transportModes": [{ "mode": "rail" }, { "mode": "metro", "subMode": "metro" }],
      "stopPlaceTypes": ["railStation", "metroStation"],
      "source": "nsr"
    }
  }],
  "bbox": [10.73350, 59.91440, 10.73350, 59.91440],
  "metadata": {
    "query": { "text": "Nationaltheatret", "limit": 1, "language": "no", "filters": { "layers": ["stopPlace"] } },
    "resultCount": 1,
    "timestamp": 1740998400000
  }
}
```

#### Reverse geocode example

**v2 request:**
```
GET /v2/reverse?point.lat=59.9110&point.lon=10.7522&boundary.circle.radius=0.5&size=1
```

**v3 request:**
```
GET /v3/reverse?lat=59.9110&lon=10.7522&radius=0.5&limit=1
```

Note: `radius` is in **kilometres** in both v2 and v3, on both autocomplete focus and reverse. Decimals are accepted (e.g. `radius=0.5` for 500 metres).
